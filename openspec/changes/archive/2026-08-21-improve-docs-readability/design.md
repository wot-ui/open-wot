## Context

`/docs` 由 `apps/website/app/docs/page.tsx` 生成页面结构，文档正文来自 `README.md`，并通过 `apps/website/app/docs/docs-source.ts` 转换为章节 HTML。页面视觉样式集中在 `apps/website/app/globals.css`，全站 `.scan-lines` 使用固定定位覆盖整个视口；文档页当前直接渲染该覆盖层，因此扫描线会叠加在所有文字上。

文档页的正文、侧边栏、目录和表格大量复用全局 `--text-muted`，不同信息层级缺少独立语义变量。主题色脚本 `apps/website/public/theme.js` 允许选择任意六位十六进制颜色，并直接将其写入 `--accent-green`；该颜色同时用于链接、行内代码和当前目录等文字，低亮度选色可能导致对比度不足。具体用户可见要求见 `specs/docs-readability/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在 `/docs` 内建立正文、辅助文字、弱化装饰和强调文字的独立颜色层级。
- 确保扫描线不覆盖文档内容，同时保留深色终端风格。
- 明确中文正文与代码内容的字体职责。
- 使默认主题色和自定义主题色下的关键文字满足对比度要求。
- 通过有限的 CSS 和主题脚本调整完成变更，避免扩大到文档生成架构。

**Non-Goals:**

- 不重写 `README.md`，不改变章节识别和 Markdown 转换逻辑。
- 不重新设计官网首页，不新增亮色主题。
- 不更换框架、引入新的 UI 或可访问性依赖。
- 不调整搜索匹配、目录激活、代码复制等交互逻辑，除非为保持视觉状态可读必须修改样式变量。

## Decisions

### 1. 在文档作用域内定义语义化文字变量

在 `.docs-site` 作用域内区分正文、辅助文字、弱化文字、边框和代码背景等语义变量，并让文档组件按信息层级引用这些变量。正文和承载关键含义的小字号文字以至少 4.5:1 为硬性门槛，正文选择更高对比度以接近 7:1 或以上；纯装饰编号和分隔线可以低于正文标准，但不能承载唯一信息。

选择局部变量而非直接提高全局 `--text-muted`，因为全局变量同时服务官网首页，直接修改会扩大视觉影响并削弱首页原有层级。也不为每个选择器继续散落硬编码灰色，以免后续再次出现不一致。

### 2. 从文档页移除覆盖式扫描线

文档页不再渲染或显示固定定位的 `.scan-lines` 覆盖层。终端感继续由深色背景、低透明度背景网格、边框、代码块和强调色提供，这些效果位于内容背后或组件自身背景中，不跨越字形。

相比仅降低扫描线透明度，完全避免覆盖更稳定：不同屏幕像素密度、缩放比例和字体渲染方式下，即使很低的不透明度也可能切过中文字形。首页是否继续使用扫描线不在本次范围内。

### 3. 仅将连续阅读内容切换为系统无衬线字体

正文段落、列表、表格描述、说明卡片和搜索输入使用中文系统无衬线字体栈；品牌、代码、命令、快捷键、代码块标签以及需要终端感的短标签继续使用 `--font-mono`。标题可以沿用现有视觉语言，但需检查中文负字距和小字号清晰度。

该方案比在 `.docs-site` 根节点整体切换字体更精确，可以避免品牌、命令和导航标签失去现有终端辨识度。正文同时控制合理字号、行高和最大阅读宽度，但不以英文 `ch` 单位作为唯一依据，优先使用适合中文段落的像素或响应式宽度上限。

### 4. 将原始主题色与可读文字色分离

保留用户选择的原始主题色用于非关键装饰边框、光晕、背景透明层和色块，同时增加一个用于文字、关键图标和焦点指示的可读强调色变量。主题脚本根据深色背景计算候选色对比度：满足 4.5:1 时直接使用原色；不满足时将候选色向白色混合或使用稳定后备色，直到满足门槛。

搜索框、主题选择器、重置按钮、复制按钮和文档操作按钮的关键焦点边框或 outline 使用可读强调色，并与实际背景保持至少 3:1 的对比度。原始主题色可以继续参与阴影和光晕，但不得成为低亮度主题下唯一的焦点指示。

不限制颜色选择器的输入范围，因为用户仍可保留品牌化装饰颜色；也不直接拒绝低亮度颜色，避免主题选择产生令人困惑的失败。计算逻辑保持轻量、无依赖，并在初始加载、选择颜色和恢复默认值时走同一流程。

### 5. 采用定向视觉检查配合现有构建验证

实现时在默认色和至少一个低亮度自定义色下检查正文、导航、搜索、表格、链接、代码和焦点状态，并覆盖桌面端与移动端视口。可使用对比度计算验证关键颜色组合，同时执行 `pnpm site:lint` 和 `pnpm site:build`。

不新增端到端测试框架；本次变更主要是视觉样式，现有仓库没有对应的浏览器视觉回归基础设施，引入它会明显扩大范围。

## Risks / Trade-offs

- [整体提亮导致页面层级变平] → 使用正文、辅助文字、弱化装饰三层语义颜色，而不是共享一个浅灰色。
- [系统字体让终端品牌感减弱] → 仅应用于连续阅读内容，品牌、命令和技术标签继续使用等宽字体。
- [主题色派生后与用户选色存在差异] → 原色继续用于非关键装饰，承载文字、关键图标和焦点指示的显示色进行可读性修正。
- [移除扫描线使页面风格变化明显] → 保留背景网格、代码块、边框和强调色，不移除整体深色终端设计语言。
- [不同组件背景导致静态颜色判断不准确] → 验证时按组件实际背景计算对比度，并避免关键文字叠加在透明且变化较大的背景上。

## Migration Plan

1. 先在文档作用域引入语义变量并迁移相关选择器，保持结构和交互不变。
2. 移除文档页扫描线节点或在文档作用域彻底禁用覆盖层，确认首页不受影响。
3. 收窄字体规则的适用范围，明确正文与技术内容的字体分工。
4. 如自定义主题色不能通过纯 CSS 保证可读性，再调整 `theme.js` 生成可读强调色变量，并将文档页关键焦点边框或 outline 迁移到该变量。
5. 完成定向检查、lint 和 build 后发布。

回滚时可恢复文档作用域的样式和主题色派生逻辑；本变更不涉及数据迁移、公共输出、持久化格式或生成配置，回滚不会影响 `README.md`、CLI、MCP 或离线数据。
